How it works

A walkthrough of what was built, why, and what was deliberately left out. No engineering background needed.

This is a ticket booking service. An event has a fixed set of seats, each priced by section. A buyer searches for an event, sees which seats are still open, and books one — first come, first served.

One thing makes that harder than it sounds, and it's what the build is really about: when two people click the same seat within the same instant, exactly one of them should get it — never both, and never neither.

The one rule that must never break: a seat is booked by at most one buyer, no matter how many people click it at the same moment.

Try it in 60 seconds

The app boots with three events and their seat inventory already seeded, and three users to book as.

  1. Open the app — pick a user from the picker, then search for an event (try "Taylor" or leave it blank).
  2. Click an event to see its seats by section, each marked Available or Booked.
  3. Book an available seat with a name and email. It flips to Booked immediately, and shows up under My tickets.
  4. Switch users from the topnav menu and try to book that same seat again — 409, because it's already gone.

What happens when a seat is booked

Three decisions worth knowing about

The booking rule is one conditional UPDATE, not a lock

update tickets set status = 'BOOKED', ... where id = :id and status = 'AVAILABLE' is the whole mechanism. Two requests racing for the same seat both run it; the database serializes the two writes, exactly one changes a row, and "rows affected" tells the service who won. No explicit lock, no read-then-write gap for a second request to slip through.

Losing the race is a 409, not a 500

"This seat is already booked" is the system working correctly, not a failure. It comes back as a normal 409 conflict with a clear reason, so a client can show "someone else got that seat" instead of a generic error.

Identity is a header, not real auth

X-User-Id states who is booking; the caller can claim any id, so this is not authentication — it's what lets "my tickets" and ownership work without building a login flow. Swapping in a verified session later is a change to one class (CurrentUser), not a rewrite of every controller.

How the pieces fit together

The data

Event

Artist and venue are attributes of the event, not their own entities — nothing here manages either on its own.

  • title, artist, venue, location, start time

Ticket

One seat at one event. Immutable price and section; status flips once.

  • section + seat label, price
  • status: AVAILABLE · BOOKED
  • buyer name/email + who booked it, once booked

User

Just enough to back the picker and "my tickets" — name and email, nothing more.

Deliberately not built

These are scoping decisions, not oversights. Each one is a conversation, not a missing feature — and each has a known shape if it becomes a requirement.

  • Real authentication. The caller states who they are in a header. Everything is wired so that swapping in real sign-in touches exactly one class.
  • Holds or a reserve/confirm flow. Booking is answered directly, in one call — there's no "reserved for 10 minutes while you check out" state. That's the natural next feature if abandoned carts become a problem.
  • Payments. Booking records who holds a seat; it doesn't move money.
  • Event or ticket creation. Events and seat inventory are fixture data — there's no admin flow to author them.
  • A real database and queues. Everything runs in memory so the whole thing starts with one command. High-demand on-sale traffic is a scaling conversation, not something half-built here.
