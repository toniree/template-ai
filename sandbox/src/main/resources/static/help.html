How it works

A walkthrough of what was built, why, and what was deliberately left out. No engineering background needed.

This is a task tracker — the sample domain this scaffold ships with. It exists to prove that persistence, validation, errors, and the UI are wired together end to end, not to model an interesting business. When a real problem shows up, this package gets replaced.

What is worth your time here isn't the task-tracking itself — it's the plumbing underneath it: a real PostgreSQL database instead of an in-memory stand-in, partial updates that can't accidentally erase a field, and error responses with a single consistent shape.

Why PostgreSQL matters here: this branch exists so that when a future feature needs a real invariant — "only one of these can happen at once" — there is a real database underneath to enforce it with a lock or a constraint, not an in-memory database that only pretends to be one.

Try it in 60 seconds

The app boots with four tasks already seeded, in a mix of statuses.

  1. Open the board — every task, its status, and when it last changed.
  2. Change a task's status from the dropdown in its row — that's a PATCH, applied immediately.
  3. Filter by status using the dropdown above the table — filtering happens in the database, not in the browser.
  4. Click a row to open its detail panel, then delete it — deleting an id that no longer exists comes back 404, not a silent success.

What happens when you edit a task

Four decisions worth knowing about

PATCH means partial, on purpose

Every field on the update request is optional and boxed (Long, not long) rather than a primitive. That matters: a primitive silently becomes 0 or false when the caller omits it, and validation would wave that through as if the caller meant it. Boxed + nullable means "not sent" and "sent as empty" stay distinguishable.

A nested resource 404s on a missing parent

There's no nested resource in this sample domain, but the rule the scaffold follows everywhere is: querying a collection under a parent id that doesn't exist must return 404, not an empty list. An empty list looks identical to "the parent is real and has nothing in it" — those are different answers, and the caller can't tell them apart otherwise.

Time comes from one injected clock

createdAt/updatedAt are stamped from a Clock bean, never Instant.now() directly. It looks identical at runtime — the payoff is in tests: an expiry or a cutoff can be tested by advancing a fake clock instead of sleeping. This sample has no expiry, but the pattern is what a feature that does would build on.

The database is real, the domain isn't (yet)

ddl-auto is create-drop: the schema is regenerated from the entities every restart, which is right while the model is still moving and wrong the moment there's a second environment to keep in sync — that's a Flyway migration away. The task domain itself has no invariant worth a lock or a constraint; when one shows up (a limit, a "one active X per Y" rule), PostgreSQL is what turns it from application logic that can be gotten wrong into something the database enforces outright.

Deliberately not built

These are scoping decisions, not oversights — this package is a wiring proof, not a product.

  • A real business domain. Task tracking has no interesting invariant on purpose. The real problem, when it arrives, replaces this package.
  • Auth. There's no identity in play in this sample, so CurrentUser isn't wired in here — it's ready for a feature that needs ownership.
  • Migrations. Schema is regenerated on every restart. A production line would start Flyway migrations from day one instead.
  • Any lock or constraint. Nothing here is contended. The PostgreSQL section of the architecture notes describes exactly which tool to reach for once something is.
